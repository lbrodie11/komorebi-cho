# CLAUDE.md — Komorebi-chō

Guidance for Claude Code (and humans) working in this repo. Read this first, every session.

## What this is
A free, web-first, cozy **living miniature** of a fictional Tokyo shitamachi backstreet. 3D scene rendered at low resolution through a palette + dither post pass so it reads as pixel art. The player places small things; residents with routines **notice and adapt**. Everything (geometry, textures, palette, music, sound) is generated by code. No purchased or commissioned assets.

**Hook:** *Build a tiny neighbourhood, then watch its people discover what you changed.*

## Non-negotiables
1. **All art and audio are code.** No image/audio/model files except generated-at-build icons. Fonts: OFL only (Pixelify Sans, Noto Sans JP), self-hosted, license file shipped.
2. **The palette is the art direction.** Every final pixel snaps to `src/render/palette.ts`. Add a colour only deliberately.
3. **No failure states, budgets or timers.** Nothing punishes the player.
4. **Never teleport a visible resident.** Disappear only into doors/exits; reappear from them.
5. **Edits are transactions.** Preview → validate → commit → resolve (nav, smart objects, residents). Removal must let occupants down gently (stand up, `?` bubble, re-plan).
6. **Determinism.** Procedural decisions use named `Rng` streams (`src/core/rng.ts`). An edit in one place must not reshuffle another.
7. **Respectful specificity.** Fictional place, fictional shop names, no real brands, no JR liveries, no real shrines/temples copied. Shrines are never "demolished for fun".
8. **Performance budget:** 60 fps on an M1/M2 MacBook Air and a mid integrated GPU at default pixel scale; idle tab costs ~0.

## Stack
TypeScript (strict) · Vite · three.js `WebGLRenderer` (r187+) · Web Audio API · Vitest · (Playwright for visual tests). No React in the render path. Pure-TS simulation (no DOM in `src/sim`, `src/world/layout.ts`, `src/world/terrain.ts`, `src/audio/theory.ts`, `src/core/*`) so it can move to a Worker later.

## Map of the code
```
src/core      rng (named streams), clock, events (typed bus), math, params (seeded-run URL)
src/render    post (pixel pass), lut (palette lookup table), camera (iso + texel snap), pixelscale (integer upscale),
              shadow (fitted sun frustum), materials (procedural textures + weathering/leaf/water/sign shaders),
              glyphs (5×5 kana, 7×7 pictograms), palette, sky (time-of-day keys)
src/world     layout (THE DATA), terrain (heights/regions), kit (geometry helpers, weathering scope, static merge),
              weathering (pure per-vertex maths), buildings, nature, props (+ placeables), crowd (light sharing),
              weather, world (assembly + time-driven updates)
src/sim       grid (nav + A*), smart (affordances/reservations), personas (the neighbours), residents (schedule → needs → utility → action),
              animals, bubbles, warmup (fixed-step warm-up for seeded runs)
src/audio     engine (graph), theory (pure), music (generative piano), ambience (soundscape), sound (facade + sfx)
src/ui        hud (DOM), build (placement tool), debug (?debug overlay), wordmark (bitmap font), style.css
src/save      storage (versioned localStorage + migrations)
tests/        vitest: core, sim, audio, render maths (lut, shadow, pixel scale), art (glyphs, weathering, leaves, sky keys)
prompts/      the roadmap: numbered work orders, done in order
docs/         ARCHITECTURE, COLOR, CONTRIBUTING, VERSIONS
```

## Commands
- `npm run dev` — local dev server
- `npm run lint` — ESLint + Prettier check; must be clean before every commit
- `npm run typecheck` — must be clean before every commit
- `npm test` — must pass before every commit
- `npm run build` — production build to `dist/`

## Working agreements
- Small, verifiable steps. After each change: typecheck, test, run the dev server and **look at it** (screenshot at Dawn/Noon/Dusk/Night and in Rain).
- New behaviour in `src/sim` or `src/audio/theory.ts` gets a unit test.
- Visual changes get a before/after screenshot in the PR description.
- Don't add dependencies without saying why; prefer writing 50 lines over adding a package.
- Keep comments for *why*, not *what*.
- Prefer data in `layout.ts` / persona tables over hard-coded logic.
