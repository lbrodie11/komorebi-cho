# 07 — Navigation v2

## Context (shared by every prompt)
You are working on **Komorebi-chō**, a free, web-first, cozy living-diorama game: a fictional Yanaka-style Tokyo shitamachi block on a walnut plinth. It's rendered in three.js (`WebGLRenderer`, r187+) at low resolution through a palette + Bayer-dither post pass, so it reads as pixel art. Residents follow schedules and a utility AI, notice what the player places, and adapt their routines. **All art and audio are generated by code.** No purchased or commissioned assets, no image or audio files.

Read `CLAUDE.md` and `docs/ARCHITECTURE.md` before touching code. Respect the non-negotiables there:
- code-only art
- the palette is law
- no fail states
- never teleport visible residents
- edits are transactions
- determinism via named RNG streams
- respectful, fictional specificity
- a 60 fps budget

Working method:

- Run the dev server and **look**: capture screenshots (Playwright or the browser) at hours 6, 12, 18 and 22, plus rain. Compare them to the screenshots from before your change.

- Finish with a short report:
  - what changed

## Goal
Navigation that never deadlocks, scales to dense player builds, and runs off the main thread.

## Tasks
1. **Worker.** Move `src/sim/*` and the nav grid into a Web Worker on a fixed 20 Hz tick with a seeded PRNG. The renderer gets transferable `Float32Array` snapshots and interpolates between them. Keep the API boundary small: commands go in (edits, time, weather), snapshots and events come out.
2. **Nav backend decision.** Profile the current grid A* with 30 agents and 40 placed objects.
   - If it's under 1 ms per tick, keep the grid, add a hierarchical layer (regions/portals) and cache paths.
   - Otherwise, evaluate `recast-navigation` (recast-navigation-js) with a **TileCache**. Its README says it assumes small tiles (around 32–64 squared), and props would become box/cylinder obstacles.

   Document the decision in `docs/NAV.md`.
3. **Local avoidance.** Residents shouldn't pass through each other. Use simple velocity-obstacle steering in open areas, or DetourCrowd if you went the recast route.
4. **Managed narrow passages** (clear width under 1.4 m: yokocho, service passages, the bridge):
   - A `PassageController` holds a direction token and an entry queue at each end.
   - Passing pockets (doorways, recesses) act as sidings.
   - Local avoidance is disabled inside the passage.
   - The token flips when the passage is empty or after a maximum wait.
5. **Crowding.** Every smart object gets a soft and a hard capacity. Desirability is multiplied by `1/(1 + density × crowdAversion)`. Queue slots form outside shops at busy times.
6. **Recovery anchors.** Every region keeps escape anchors (doors, street nodes, exits). On commit, flood-fill connectivity. Agents on islands path to an anchor, or fade only while occluded or off-screen.
7. **Off-mesh links** for doors, stairs, the shrine steps, and cat jumps between ledges (cats get their own agent profile: radius 0.15 m, climb 0.6 m).

## Acceptance criteria
- A 10-minute automated fuzz (random edits every 2 s, with fast-forward) gives zero agents stuck for more than 5 s and zero deadlocks in the alley or on the bridge.
- The main-thread frame time no longer includes sim cost (show the profile).
- 40 residents and 60 placed objects run at 60 fps on the reference laptop.
